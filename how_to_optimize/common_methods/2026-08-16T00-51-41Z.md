# Common methods for optimizing trunk inference

This is a source-grounded option survey, not a performance result. No benchmark was run as part of this research. “Expected fit” below is an engineering judgment based on this repository’s current architecture; every candidate still needs an end-to-end accuracy and performance comparison on the target GPU.

## Short answer

The strongest first pass for this repository is:

1. Establish a reproducible eager baseline, profile by encoder/tower/decoder/head, and report both single-example latency and steady-state throughput.
2. Make the intended workload explicit: request only required heads and resolutions, batch independent reference/alternate sequences when memory permits, and use `model.eval()` plus `torch.inference_mode()`.
3. Benchmark the existing BF16 policy and a fixed-shape `torch.compile(..., backend="inductor")` path. Try `default`, `max-autotune-no-cudagraphs`, then CUDA-graph modes separately so their effects remain attributable.
4. Remove model-specific repeated work: fold `StandardizedConv1d` weights for frozen inference and cache fixed-shape RoPE/relative-position tensors.
5. If profiling confirms the tower is dominant, prototype a fused attention implementation that exactly preserves grouped-query attention, the learned dense pair bias, FP32 score/softmax behavior, and the tanh soft cap. FlexAttention, FlashAttention with extensions, or a purpose-built Triton/CUDA kernel are candidates; ordinary SDPA is not mathematically equivalent as written.
6. Evaluate TensorRT/Torch-TensorRT, quantization, ONNX Runtime, and single-request multi-GPU partitioning only after the native PyTorch path is measured and numerically locked down.

## Why this model needs a tailored approach

The normal input is `(B, 131072, 4)`. Six encoder down-blocks plus pooling reduce it to a `(B, 1536, 1024)` trunk, after which nine transformer blocks operate on 1,024 tokens; five of those blocks update pair state ([model source](../../src/alphagenome_pytorch/model.py#L14-L136)). The transformer MHA is an 8-query-head/1-key-head/1-value-head grouped-query pattern with query/key width 128 and value width 192. It explicitly materializes FP32 `(B, 8, 1024, 1024)` scores, adds a learned dense pair-derived bias, applies `5 * tanh(score / 5)`, softmaxes, and then multiplies values ([attention source](../../src/alphagenome_pytorch/attention.py#L145-L206)). At batch size one, each such FP32 score-sized tensor is about 32 MiB, derived directly from those shapes.

The pair update first pools the 1,024-token trunk by 16, producing a `64 x 64 x 128` pair representation. Its row attention and pair MLP run at that lower resolution, but each transformer block’s bias projection repeats the pair grid back to `1024 x 1024 x 8` ([attention source](../../src/alphagenome_pytorch/attention.py#L222-L374)). This makes the learned bias and soft cap central compatibility constraints for fused-attention work.

The high-resolution convolutional path can also dominate memory and compute. When 1 bp output is requested, the decoder returns `(B, 768, 131072)` and the 1 bp embedder returns `(B, 1536, 131072)`; omitting resolution 1 already skips the decoder ([model source](../../src/alphagenome_pytorch/model.py#L542-L599)). The latter embedding alone contains 201,326,592 values per sample—about 384 MiB in BF16 or 768 MiB in FP32—before output heads. Therefore “trunk speed” should be measured separately from full-model latency.

Two additional repository-specific opportunities are visible without profiling:

- Every `StandardizedConv1d.forward` recomputes weight mean, variance, reciprocal square root, and scaled weights even in eval mode. Frozen inference can pre-fold that expression into ordinary convolution weights, with parity tests and a clear policy for invalidating/rebuilding folded weights after loading or fine-tuning ([convolution source](../../src/alphagenome_pytorch/convolutions.py#L5-L46)).
- Each MHA invocation regenerates fixed-position RoPE frequencies, angles, sine, and cosine; each pair update also recreates fixed relative-position base features. For fixed 1,024-token trunks these shape/device/dtype-dependent tensors can be cached or made compiler-visible constants ([attention source](../../src/alphagenome_pytorch/attention.py#L15-L87), [pair-position source](../../src/alphagenome_pytorch/attention.py#L264-L301)).

## Keep techniques separate from runtimes

| Kind | Popular options | What it changes |
|---|---|---|
| Measurement | `torch.utils.benchmark`, `torch.profiler`, Nsight Systems/Compute | Establishes latency, throughput, memory, launch, and kernel bottlenecks; it does not optimize execution by itself. |
| Execution discipline | inference mode, batching, fixed shapes/bucketing, output pruning, preallocation | Removes avoidable work or improves hardware utilization while remaining in the same runtime. |
| Numerical technique | BF16/FP16, TF32, FP8/INT8/INT4 quantization | Changes arithmetic/storage precision; speed depends on operator and hardware support and requires accuracy validation. |
| Graph compiler | `torch.compile` with TorchInductor | Captures PyTorch graphs and can fuse/reorder/generate kernels. Inductor may generate Triton kernels on NVIDIA GPUs. |
| Kernel primitive/DSL | PyTorch SDPA/FlexAttention, FlashAttention, Triton, custom CUDA/C++ | Replaces or fuses one hotspot. Triton is a kernel language/compiler, not an end-to-end serving runtime. |
| Deployment compiler/runtime | TensorRT, Torch-TensorRT, ONNX Runtime execution providers | Converts/partitions a graph for a deployment engine; unsupported operations and graph boundaries determine the benefit. |
| Parallelization | replicated workers, tensor/sequence/pipeline parallelism | Trades additional devices and communication for throughput, memory capacity, or sometimes latency. |

PyTorch documents `torch.compile`’s default Inductor backend, static/dynamic specialization, recompilation guards, and modes including `reduce-overhead` and `max-autotune`; the latter can use Triton/template matmuls and Triton convolutions on supported GPUs ([`torch.compile` reference](https://docs.pytorch.org/docs/stable/generated/torch.compile.html)). Triton itself is intended for high-performance custom deep-learning primitives and provides official fused-softmax, matmul, layer-norm, and fused-attention tutorials ([Triton tutorials](https://triton-lang.org/main/getting-started/tutorials/), [Triton project](https://github.com/triton-lang/triton)).

## Ranked options for this repository

“Risk” combines numerical-parity, maintenance, export, and portability risk. Rankings assume NVIDIA GPU inference on repeated 131,072-base inputs; CPU or edge deployment would change them.

| Rank | Option | Expected fit | Effort | Risk | Primary reason |
|---:|---|---|---|---|---|
| 1 | Profile + prune heads/resolutions + correct inference context | Very high | Low | Low | Prevents optimizing unused decoder/head work and creates an honest baseline. |
| 2 | Existing BF16 policy; TF32 as FP32 fallback experiment | Very high | Low | Medium | Conv/linear/matmul-heavy model; precision changes need biological-output parity checks. |
| 3 | Frozen-convolution folding + position caches | High | Medium | Medium | Removes repeated, mathematically redundant work specific to this implementation. |
| 4 | Fixed-shape `torch.compile`/Inductor | High | Low–medium | Medium | Least disruptive route to fusion and generated kernels; graph breaks/compile time must be measured. |
| 5 | Fused MHA preserving bias + soft cap (FlexAttention/FlashAttention/custom Triton or CUDA) | High if tower dominates | High | High | Avoids materializing large score/weight tensors, but exact semantics are nonstandard. |
| 6 | Batching + CUDA Graphs | Medium–high | Medium | Low–medium | Improves throughput and/or launch overhead when shapes and memory addresses are stable. |
| 7 | TensorRT/Torch-TensorRT | Medium | High | High | Mature NVIDIA engine, but custom math, dynamic Python control flow, and coverage/fallback boundaries may limit fusion. |
| 8 | Selective FP8/INT8/weight-only quantization | Medium | Medium–high | High | Could accelerate large linear/conv weights on suitable hardware, but this is not a standard decoder-only LLM and accuracy sensitivity is unknown. |
| 9 | Replicated multi-GPU inference | High for aggregate throughput; none for one-request latency | Low–medium | Low | Independent samples/requests scale without partitioning the model. |
| 10 | Tensor/true sequence parallelism for one request | Low–medium | High | High | Useful for capacity; communication and the dense global tower may erase latency gains. |
| 11 | ONNX Runtime | Medium–low as a speed project; high for portability | High | Medium–high | Valuable deployment abstraction, but export/partition coverage must be demonstrated; it is not automatically faster. |

## Measurement and baseline

Use one pinned hardware/software configuration and record GPU model, driver, CUDA, cuDNN, PyTorch, dtype, batch, heads, resolutions, input shape, output layout, warmup count, and whether compile/graph capture is included. Report:

- cold-start/compile/engine-build time separately from warmed execution;
- p50/p95 latency for `B=1` and steady-state samples/second for realistic batches;
- peak allocated/reserved memory and host-to-device/device-to-host time;
- stage timings for encoder, transformer tower, decoder/embedders, and heads;
- kernel time, launch gaps, graph breaks/recompiles, and output-transfer/serialization time.

`torch.utils.benchmark.Timer` performs warmups, synchronizes asynchronous accelerators when needed, and encourages replicated measurements/medians ([benchmark utility](https://docs.pytorch.org/docs/stable/benchmark_utils.html)). `torch.profiler` records operator shapes/stacks and CPU/device kernel activity for inference ([profiler reference](https://docs.pytorch.org/docs/stable/profiler.html)). Use profiler schedules only for short diagnostic windows because profiling changes timing; use CUDA events or the benchmark utility for final steady-state timing. Add NVTX ranges around model stages when using Nsight.

Always compare the same workload. This model already accepts `heads=...`, `resolutions=(128,)`, `embeddings_only`, and `encoder_only`; the public prediction paths use `torch.no_grad()` rather than inference mode ([forward source](../../src/alphagenome_pytorch/model.py#L681-L868), [prediction runtime](../../src/alphagenome_pytorch/prediction.py#L133-L190)). A useful benchmark matrix is encoder-only, trunk embeddings, 128 bp selected heads, 1 bp selected heads, contact maps, splicing, and all outputs.

## Low-risk execution changes

### Inference mode and output pruning

For outputs that will never re-enter autograd, benchmark replacing `no_grad` with `torch.inference_mode()` while still calling `model.eval()`. PyTorch says inference mode additionally disables view tracking and version-counter bumps, but tensors created inside it cannot later participate in autograd-recorded computation; inference mode also does not set eval mode automatically ([inference mode reference](https://docs.pytorch.org/docs/stable/generated/torch.autograd.grad_mode.inference_mode.html)). Keep `encode()` grad-capable for fine-tuning and make the stronger context a serving/prediction concern.

Infer `resolutions` from requested heads where safe, and do not construct/return pair embeddings unless contact maps or pair embeddings are requested. The tower’s pair state cannot simply be removed because it generates the learned bias used by every MHA block, but the final pair output projection can be conditional ([tower and embedding path](../../src/alphagenome_pytorch/model.py#L115-L136), [embedding path](../../src/alphagenome_pytorch/model.py#L571-L599)).

### Batching, static shapes, and input/output movement

Batch independent examples to improve throughput until memory or latency targets intervene. In particular, reference and alternate allele predictions are currently executed serially; stacking them into a batch is a concrete experiment when memory permits ([prediction runtime](../../src/alphagenome_pytorch/prediction.py#L163-L205)). Memory scales sharply with batch because MHA materializes dense score tensors and 1 bp embeddings, so measure rather than assume a larger batch wins.

Keep the canonical sequence/trunk lengths static for compiler and graph experiments. If production lengths vary, bucket/pad deliberately and validate that padding/cropping preserves model semantics. Static shape/dtype/control-flow paths avoid repeated compiler specializations; `torch.compile` documents guard-driven recompilation and fallback behavior ([`torch.compile` reference](https://docs.pytorch.org/docs/stable/generated/torch.compile.html)). Reuse device input/output buffers and defer CPU copies/serialization when measuring GPU inference.

## Precision

The repository already has `DtypePolicy.mixed_precision()` with FP32 parameters and BF16 compute/output, and `encode()`/`predict()` use autocast around the compute path ([dtype policy](../../src/alphagenome_pytorch/config.py#L18-L61), [model autocast](../../src/alphagenome_pytorch/model.py#L643-L665)). PyTorch’s AMP policy runs eligible convolutions, linears, and matmuls in lower precision while operations such as softmax and layer norm may run in FP32 for stability ([AMP reference](https://docs.pytorch.org/docs/stable/amp.html)). Benchmark BF16 first on `torch.cuda.is_bf16_supported()` hardware, but verify per-head outputs and downstream variant-score tolerances against the reference—not only aggregate correlation.

For an FP32 compatibility path on Ampere-or-later NVIDIA GPUs, TF32 is worth an explicit benchmark. PyTorch documents that TF32 can accelerate FP32 matmuls/convolutions by using reduced mantissa precision with FP32 dynamic range/accumulation, and warns that accuracy differs from full FP32 ([CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html#tensorfloat-32-tf32-on-ampere-and-later-devices), [numerical accuracy](https://docs.pytorch.org/docs/stable/notes/numerical_accuracy.html#tensorfloat-32-tf32-on-nvidia-ampere-and-later-devices)). Do not combine BF16, TF32, compile, and a kernel rewrite in one first measurement; isolate effects.

## `torch.compile` / TorchInductor

This is the best general compiler to try first because it stays inside the existing PyTorch program. Start with a fixed input shape and stable `heads`/`resolutions`, compile a focused callable (tower first if full-model tracing is brittle), warm it fully, then compare `default`, `max-autotune-no-cudagraphs`, and graph-enabled modes. Use `torch._dynamo.explain`/compiler logs to find graph breaks and recompiles; graph breaks split optimization regions and lose fusion opportunities ([compiler troubleshooting](https://docs.pytorch.org/docs/stable/user_guide/torch_compiler/torch.compiler_troubleshooting.html)).

Compatibility cautions:

- The project declares only `torch>=2.0.0`, while current compiler, FlexAttention, and distributed capabilities are version-sensitive; any optimized path needs a tested PyTorch/CUDA compatibility matrix rather than relying on that broad lower bound ([project dependency](../../pyproject.toml#L7-L18)).
- Compilation has cold-start and warmup costs. Cache where supported and report amortization separately.
- Python dictionaries, optional outputs, hooks, data-dependent splice-site selection, and in-place/view behavior can create specializations or breaks; compile the smallest stable unit first.
- Validate eager-versus-compiled outputs for all supported heads and both dtypes before making it a default.

## Fused attention, FlashAttention, Triton, and custom CUDA

PyTorch SDPA is a popular first choice because it accepts grouped-query attention and a broadcastable additive mask, and dispatches among optimized and fallback implementations ([SDPA reference](https://docs.pytorch.org/docs/stable/generated/torch.nn.functional.scaled_dot_product_attention)). The current 8:1 query-to-KV head ratio satisfies SDPA’s documented GQA divisibility constraint, and SDPA permits value width `Ev` to differ from query/key width. However, its operation is essentially `softmax(scale * QKᵀ + bias) V`; this model performs `softmax(5*tanh((scale * QKᵀ + learned_bias)/5)) V`. Since SDPA has no soft-cap hook, a direct substitution changes the model.

Better prototypes are:

1. **FlexAttention:** it exposes an arbitrary score modification before softmax and supports GQA, so the learned indexed bias plus tanh soft cap can be expressed in principle. PyTorch notes that FlexAttention needs compilation for good performance ([FlexAttention reference](https://docs.pytorch.org/docs/stable/nn.attention.flex_attention.html), [PyTorch transformer building blocks](https://docs.pytorch.org/tutorials/intermediate/transformer_building_blocks.html)). Verify support for this model’s value width, dense bias access pattern, BF16 inputs/FP32-equivalent accumulation, and target GPU/PyTorch version.
2. **FlashAttention package:** the owning project supports grouped-query attention and attention soft-capping, but its stock interfaces and supported bias forms still need a coverage check for this learned per-batch/per-head dense bias ([official FlashAttention repository](https://github.com/Dao-AILab/flash-attention)).
3. **Purpose-built Triton or CUDA:** fuse QK, learned bias load, soft cap, online softmax, and PV without writing the full score/weight matrices to HBM. Triton’s official fused-attention tutorial demonstrates the tiled online-softmax structure, but this repository needs extra bias, GQA, unequal value width, exact dtype behavior, and robust tail/layout handling ([Triton fused-attention tutorial](https://triton-lang.org/main/getting-started/tutorials/06-fused-attention.html)). Custom CUDA offers maximum control and maintenance cost.

Also profile `RowAttentionBlock`: it explicitly materializes `64 x 64` row-attention scores for every leading row/batch and is another possible fused kernel, though it is much smaller than trunk MHA ([row-attention source](../../src/alphagenome_pytorch/attention.py#L305-L337)). Write reference tests around Q/K/V projections, score bias, soft cap, softmax, output, and full downstream heads; do not accept a kernel based only on speed.

## CUDA Graphs

CUDA Graphs capture a fixed sequence of CUDA work for replay, reducing repeated CPU launch overhead. PyTorch documents that graph replay relies on the same kernels, arguments/dependencies, and memory addresses; arbitrary control flow is restricted ([PyTorch CUDA Graph trees](https://docs.pytorch.org/docs/stable/user_guide/torch_compiler/torch.compiler_cudagraph_trees.html), [`torch.cuda.graph`](https://docs.pytorch.org/docs/stable/generated/torch.cuda.graph.html)). That makes the canonical fixed input and fixed head/resolution selection a plausible fit, but only if profiling shows launch gaps matter relative to large convolution/matmul kernels.

Try compiler-managed graphs before manual capture. `torch.compile(mode="reduce-overhead")` uses CUDA graphs where applicable but can increase memory and is aimed at launch-overhead-bound workloads; `max-autotune` enables graphs on GPU, while `max-autotune-no-cudagraphs` isolates autotuning from graph capture ([`torch.compile` reference](https://docs.pytorch.org/docs/stable/generated/torch.compile.html)). Manual graphs require long-lived static buffers and careful output-lifetime handling.

## TensorRT and Torch-TensorRT

TensorRT is a popular NVIDIA deployment compiler/runtime with tactic selection, layer/pointwise fusion, multiple precisions, batching, CUDA Graphs, and multi-streaming ([TensorRT optimization guide](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/optimization.html), [precision control](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/precision-control.html)). Torch-TensorRT can compile PyTorch in process via a `torch.compile` backend, avoiding a mandatory intermediate ONNX file.

Treat it as a later feasibility spike:

- Run Torch-TensorRT’s operator-coverage dry run and inspect every fallback/partition. Its documentation recommends `dynamic=False` because new batch sizes currently trigger recompilation in that backend, and describes using `torch._dynamo.explain` to find graph breaks ([Torch-TensorRT compile backend](https://docs.pytorch.org/TensorRT/user_guide/compilation/torch_compile.html)).
- Prefer a fixed-shape engine for the canonical workload. TensorRT supports dynamic shapes via build-time min/opt/max optimization profiles, but shape/profile changes have overhead and may choose less specialized tactics ([dynamic-shape guide](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/work-with-dynamic-shapes.html)).
- Expect work around custom normalization/weight standardization, RoPE, pair einsums, soft cap, dictionaries/optional outputs, and splice-site generation. Unsupported islands can erase gains through graph fragmentation or transfers.
- Compare end-to-end latency including bindings/copies, engine build/cache behavior, and exact per-head outputs. TensorRT explicitly treats reduced precision as an accuracy/performance tradeoff and provides per-layer precision controls ([TensorRT optimization guide](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/optimization.html#tradeoffs-between-accuracy-and-performance)).

## ONNX Runtime

ONNX Runtime is primarily a portable inference runtime. It performs graph optimizations and partitions supported subgraphs among execution providers such as CUDA and TensorRT, falling back for unsupported portions ([execution providers](https://onnxruntime.ai/docs/execution-providers/), [runtime architecture](https://onnxruntime.ai/docs/reference/high-level-design.html)). That makes it useful if deployment outside Python/PyTorch is a requirement, but it is not evidence of a speedup by itself.

Export a narrow fixed-output callable rather than the whole dynamic API, then inspect graph validity, numerical parity, provider assignment, fallback nodes, and transfers. The model’s nonstandard attention and Python-level output/control flow make export and fusion coverage the main risks. ORT’s own documentation says users are responsible for validating accuracy, performance, and suitability ([ONNX Runtime overview](https://onnxruntime.ai/docs/)). If the desired endpoint is NVIDIA TensorRT, compare direct Torch-TensorRT against ONNX→TensorRT EP rather than assuming the extra representation improves results.

## Quantization

Popular schemes include weight-only INT8/INT4, dynamic activation+weight INT8/FP8, post-training static INT8 with calibration, and quantization-aware training. torchao separates quantization algorithms, quantized tensor representations, and the efficient kernels that actually realize speed; its support matrix varies by dtype and hardware ([torchao overview](https://docs.pytorch.org/ao/stable/contributing/quantization_overview.html), [torchao workflow matrix](https://docs.pytorch.org/ao/stable/workflows/index.html)). ONNX Runtime similarly notes that GPU quantization speed needs appropriate hardware and that quantize/dequantize overhead can make performance worse ([ORT quantization guide](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)).

For this model, start selectively with the large `nn.Linear` projections/MLPs, then consider convolution support on the exact hardware/backend. Do not assume LLM-oriented weight-only recipes optimize the high-resolution convolutional path, pair einsums, softmax, or custom ops. Quantization should follow an accuracy protocol spanning embedding error, every requested head, contact maps/splicing, and the downstream variant-scoring decisions; calibration data must represent both organisms and realistic sequence distributions. BF16 is the lower-risk reduced-precision baseline.

## Multi-GPU and distributed inference

For aggregate throughput, the simplest popular option is one model replica/process per GPU with independent requests or batch shards. It avoids collectives during each forward and is usually the first distributed benchmark when the model fits on one GPU.

For one-request capacity/latency, distinguish the repository’s existing sequence-parallel helper from true tower partitioning. It shards the high-resolution encoder/decoder, then all-gathers the complete 1,024-token trunk and runs the full transformer tower on every rank before scattering again ([sequence-parallel source](../../src/alphagenome_pytorch/sequence_parallel.py#L290-L412)). It can reduce high-resolution activation memory, but it replicates the likely dense-tower hotspot and adds collectives; therefore it should not be presented as a trunk speedup without measurements.

Tensor parallelism could shard large linear projections and attention heads, but introduces collectives and substantial integration work. PyTorch provides row-wise, column-wise, and sequence-parallel styles on DTensor, while marking the API experimental ([PyTorch tensor parallel reference](https://docs.pytorch.org/docs/stable/distributed.tensor.parallel.html)). A true pair/tower partition must also distribute or communicate the learned dense bias and pair updates. Pipeline parallelism is another option but is generally throughput-oriented and can have bubbles for batch-one latency. Measure replicated throughput first, then pursue model partitioning only for a concrete memory or single-request service-level objective.

## Proposed experiment order and acceptance gates

1. **Baseline harness:** fixed corpus and configuration; stage NVTX ranges; eager FP32/BF16; correct synchronization; cold and warm metrics.
2. **No-math-change wins:** selected heads/resolutions, inference mode, batched ref/alt where memory allows, delayed CPU transfer.
3. **Repository-specific cleanup:** fold frozen standardized convolutions; cache RoPE and base relative-position features; verify parity.
4. **Native compiler:** fixed-shape Inductor, first tower-only and then full selected-output callable; log breaks/recompiles and compile amortization.
5. **Attention prototype:** FlexAttention first if it can encode the exact score modification on the pinned stack; otherwise FlashAttention extension or a Triton kernel. Compare score/output tensors and all downstream outputs.
6. **Launch/throughput tuning:** batch sweep and CUDA Graphs after stable static execution exists.
7. **Deployment/precision spikes:** Torch-TensorRT coverage, then selective quantization; ONNX Runtime only when its deployment properties are valuable.
8. **Multi-GPU:** replicated workers for throughput; true tower partitioning only if single-GPU capacity/latency remains the blocker.

For every step, require: no missing/extra outputs; shape/dtype parity; defined absolute/relative tolerances per output family; agreement on variant rankings/threshold decisions; peak-memory and latency/throughput improvement on repeated runs; and a documented fallback for unsupported hardware or shapes. Keep optimization flags opt-in until this matrix is covered.
