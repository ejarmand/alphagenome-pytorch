# Reply: reprioritizing for million-variant batch scoring

**Reply-to:** `2026-08-16T00-51-41Z.md` (Common methods for optimizing trunk inference)

The parent survey is sound, but it optimizes for single-request latency. The actual target
workload is **batched scoring of millions of variants from VCFs** — a throughput problem.
That reorders the priorities and adds a pipeline dimension (VCF parsing, sequence
extraction, one-hot encoding, host-to-device transfer) the parent doc doesn't cover.

## What the current scoring path actually does

Grounded in this worktree's source:

- `AlphaGenomePredictionRuntime.predict_variant` fetches ref and alt sequences from FASTA
  in Python, then runs **two serial batch-1 forwards** per variant
  ([prediction source](../../src/alphagenome_pytorch/prediction.py#L163-L205)).
- The optional `to_cpu` path calls `gc.collect()` and `torch.cuda.empty_cache()` **per
  variant** — both are expensive and neither should run inside a hot loop.
- `VariantScorer.score_variants` fans variants out over a `ThreadPoolExecutor`
  ([scorer source](../../src/alphagenome_pytorch/extensions/serving/scorer.py#L125-L177]).
  Under the GIL with a single CUDA stream this does **not** parallelize GPU work; each
  thread still issues serial batch-1 forwards, plus contention. It only hides CPU
  sequence-fetch latency.
- Deletion handling pads then crops so ref/alt are always the same fixed length — static
  shapes hold, which keeps compile/CUDA-graph options open.

So today the effective throughput unit is ~2 batch-1 forwards + Python glue per variant.
At millions of variants, every structural inefficiency here multiplies by 10⁶.

## Reordered priorities for this workload

1. **End-to-end throughput baseline (variants/sec from VCF to scores).** Extend
   `scripts/benchmark_performance.py` (which already does stage profiling and hardware
   capture) with a variant-scoring mode: N variants from a real VCF, measure VCF parse,
   sequence fetch, one-hot, H2D, forward, scoring reduction, D2H separately. Without this
   we can't tell whether the GPU is even the bottleneck — with batch-1 forwards and
   Python-side FASTA fetches it plausibly is not.

2. **Batch the forwards.** This is the single largest expected win and costs no numerics:
   - Stack ref+alt into one batch (immediate 2× fewer launches).
   - Then batch across variants: B sequences per forward, B limited by the FP32
     `(B, 8, 1024, 1024)` score tensors (~32 MiB each × 9 blocks) and, if requested, the
     1 bp path. With 128 bp-only heads, B=8–32 should fit on a modern GPU; measure.
   - Scoring reductions (`_scores_to_anndata` etc.) must become batch-aware or run on a
     separate CPU thread consuming completed batches.

3. **Producer/consumer input pipeline.** Replace the ThreadPoolExecutor-around-forwards
   pattern with: CPU worker pool doing VCF→interval→FASTA fetch→one-hot into **pinned,
   reused buffers**, a bounded queue, and a single GPU consumer doing async
   `copy_(non_blocking=True)` + forward, double-buffered so H2D overlaps compute. One-hot
   encoding of a 131 kb sequence is a numpy byte-LUT operation, trivially parallel across
   workers. Use `cyvcf2` (or polars over a pre-flattened variant table) instead of
   line-by-line Python VCF parsing; keep `pysam`/`pyfaidx` handles per-worker.

4. **Ref-sharing across variants.** Ref and alt forwards are currently 50 % of compute.
   Options, in increasing semantic impact:
   - Exact dedup: variants sharing the exact same window reuse one cached ref prediction
     (the ISM path already does this on main — "Cache reference prediction in
     score_ism_variants").
   - Window snapping: round window starts to a 128 bp grid so nearby variants share a ref
     window. For dense VCFs (e.g. all variants in a locus, GWAS fine-mapping sets) this
     can approach 2× plus cache hits across alts at the same site (multi-allelic).
     Snapping means the variant is no longer exactly centered — needs a documented
     accuracy check against centered scoring before adoption.

5. **Output pruning + inference mode + hot-loop hygiene** (parent doc rank 1, still top
   tier): request only the heads/resolutions the scorers consume — skipping the 1 bp
   decoder/embedder path removes the largest activations and directly raises max batch
   size. Switch the scoring loop to `torch.inference_mode()`, delete the per-variant
   `gc.collect()`/`empty_cache()`, and keep outputs on GPU through the scoring reduction,
   transferring only the final per-variant score vectors.

6. **BF16 (existing policy) + conv folding + RoPE/relative-position caches** (parent doc
   ranks 2–3). Unchanged, all amortize perfectly over millions of calls. The
   `StandardizedConv1d` fold and position caches are pure wins for a frozen model.

7. **Fixed-shape `torch.compile`, then CUDA graphs.** The variant workload is the ideal
   compile client: one shape, one head set, millions of replays. Compile the smallest
   stable callable (tower first). `mode="reduce-overhead"` graphs matter more here than
   in the latency framing because per-forward Python/launch overhead is paid 10⁶ times.

8. **Fused attention (FlexAttention first).** Same analysis as the parent doc; for
   throughput its main value is **memory**: eliminating the materialized FP32 score
   tensors raises max batch, which compounds with step 2. Prototype only after profiling
   confirms the tower dominates at the chosen batch size. FlexAttention's `score_mod` can
   express `5*tanh((qk + bias)/5)` and it composes with `torch.compile`; verify the
   192-wide value head and dense per-head bias load on the pinned PyTorch version.

9. **Replicated multi-GPU.** Parent doc rank 9, but for this workload it is near-top:
   shard the VCF across one worker process per GPU, no collectives, linear scaling.
   Cheap to build once the single-GPU pipeline (steps 2–3) exists — the same
   producer/consumer code runs per shard.

Deprioritized relative to the parent doc: TensorRT/ONNX (high effort, and steps 2–7
likely saturate the GPU first), quantization (accuracy risk with no throughput ceiling
yet demonstrated), tensor/sequence parallelism (wrong tool — no single-request latency
or capacity constraint here).

## Concrete next steps

1. Add a `--variants N --vcf ... --fasta ...` mode to `scripts/benchmark_performance.py`
   reporting stage-wise time and variants/sec; run it on the target GPU with the real
   head/resolution selection to get the baseline and the bottleneck split (CPU vs H2D vs
   GPU).
2. Implement batched `predict_variants` (stacked ref/alt, batch across variants) with a
   pinned-buffer producer/consumer loop; re-benchmark.
3. Apply step 5 hygiene (inference_mode, no per-variant gc, GPU-side reductions, pruned
   outputs) in the same pass — small diffs, same test surface.
4. Then conv folding + position caches with parity tests, then compile, then the
   FlexAttention spike — each gated by the parent doc's acceptance criteria (parity on
   all requested heads, agreement on variant rankings, measured variants/sec gain).

Acceptance metric for every step: **variants/sec end-to-end from VCF** on the pinned
hardware config, plus score parity (rank agreement on a fixed 10 k-variant reference set)
— not kernel microbenchmarks.
